# 学习笔记模板

用于代码对话、bug 修复、需求开发、代码解释和实现复盘。

## 写作原则

这不是会议纪要，也不是完整教程。

要写成以后能快速复盘的工程笔记：

- 主线清楚：问题、设计、实现、复盘点。
- 优先记录具体模块、文件、函数、状态、数据流和用户操作。
- 只有在对话、diff 或本地文件里能拿到真实代码时，才写代码片段。
- 不得编造文件名、变量名、接口、业务流程或验证结果。
- 不要扩展成百科式教程，只解释理解本次任务需要的内容。

## 固定结构

```markdown
# 主题名

## 问题/目标

用 1-3 句话说明。

如果是 bug，写清原问题、触发条件和期望结果。
如果是新需求，写清功能目标和业务价值。
如果是代码解释，写清这次要理解的模块或概念。

## 设计思路

先讲整体策略，再讲单个代码点。

遇到完整模块或多处协作改动时，尽量按这个顺序讲：

1. 整体设计。
2. 状态变量或派生数据。
3. 页面展示。
4. 用户点击或选择。
5. 校验、拦截、提交或重置。

没有出现在真实材料里的环节直接跳过，不要补写。

## 实现讲解

按组件、文件或数据流顺序写。

每个相关模块讲清：

- 模块职责。
- 为什么需要改，或为什么它是理解重点。
- 真实代码片段，前提是材料里确实有。
- 关键语句做了什么。
- 数据如何进入、流转和离开这个模块。

如果能拿到改动前后，就做对比。

如果用户追问过某个语法或代码行，把解释放到对应模块里，不要单独写成百科小节。

## 复盘点

写 1-3 条：

- 本次修复或实现的核心判断。
- 下次遇到类似问题时优先检查什么。
- 哪个语法、状态设计或数据流最容易忘。
```

## 代码片段规则

每段代码前先说明：这段代码解决什么问题。

每段代码后面紧跟解释，不要把语法解释挪到很远的地方。

代码片段要短，只作为定位锚点，不整段复制源码。

解释 `slice`、`map`、`filter`、`computed`、`watch`、`nextTick`、`props`、`emit`、`v-if`、`v-show`、`:class`、`:disabled`、`@click` 等语法时，至少讲清：

- 它做什么。
- 关键参数或分支是什么意思。
- 是否会修改原数据。
- 为什么本次任务需要这样写。
